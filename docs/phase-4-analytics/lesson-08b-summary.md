# Lesson 8b: Historical Monthly Data & Fact Constellation

## Overview

The goal was to compare this year's data against historical averages in Power BI. The first plan was to backfill daily history (2000 onward) into the existing fact table. It was abandoned after the write bottleneck and the 2 GB storage limit made it impractical. Since a comparison against averages doesn't need daily granularity, the plan changed to monthly data from MeteoSchweiz's `_m` files, held in a second fact table at its own grain.

## What Happened

### Daily backfill attempt
- Downloaded `_d_historical` files, filtered them locally to 2000 onward (a one-time step, so it didn't belong in the recurring notebook), uploaded them to ADLS, and extended `dim_date` to 2000–2026 (9,862 rows).
- A separate one-time notebook wrote the historical data to `processed/historical` (Parquet, so the current-year output wasn't overwritten) and appended it to `[lf-ogd-smn_d]` with `mode="append"`.
- The unpivoted historical DataFrame had **57,445,830 rows**, about 37x the original load. The write was chunked **by year** with manual verification after each year, instead of one multi-hour write.
- Filtering and writing must use the joined DataFrame (`df_long_dim`). The pre-join `df_long` has no surrogate keys.

### Write performance
| Setting | Time per year |
|---|---|
| Basic tier, `numPartitions=1` | ~28 min |
| Basic tier, `numPartitions=4` | ~35 min |
| Temporarily scaled to 100 DTU (Standard), `numPartitions=1` | ~3.5 min |

- More partitions made the write slower, consistent with the transaction log write-rate cap (`LOG_RATE_GOVERNOR`) being the limit rather than concurrency. This fits the result but isn't proven.
- Scaling up cut the time about 8x, which supports the earlier diagnosis that Basic tier was the constraint.
- Cost at 100 DTU was roughly $0.235/hour (the portal showed ~$172/month for continuous use). Azure SQL does not scale back down on its own, so the revert needed a reminder.

### Storage limit and why the plan changed
- The database hit the 2 GB Basic ceiling while backfilling. Scaling up had not raised the max size setting, which is separate from the DTU slider.
- A database's size on disk is much larger than the raw CSVs. Unpivoting multiplies the row count, and indexes, constraints and the transaction log all take space.
- Basic tier's 2 GB cap would not have held the full daily history at any tier of effort, so reverting to Basic would have been impossible.
- The partially loaded historical rows were deleted and the database went back to Basic.
- A single `DELETE` over the whole table timed out. Deleting one year at a time took about 3 minutes per year. The likely cause is that `YEAR(reference_timestamp)` has to be evaluated against every row in the table, but this is a hypothesis, not confirmed.
- `DELETE` doesn't return space to the database file. Microsoft's documentation describes `DBCC SHRINKDATABASE` as the way to reclaim it after a large delete. Shrinking fragments indexes and can run for a long time.

### Rescoping to monthly data
- The `_m` files have the same structure as the `_d` files, with timestamps on the first of each month.
- A rough row estimate (158 stations × 12 months × ~39 parameters ≈ 70,000 rows/year) showed that even 100 years would use about half the row count that got close to 2 GB with daily data. The estimate is approximate.
- The range was capped at **1975 onward (50 years)**, which is enough for the comparison and leaves plenty of margin.

## Design Decisions

### Separate fact table, not a mixed grain
Mixing daily and monthly rows in one table would leave what a row means ambiguous. Two fact tables at different grains sharing common dimensions is a **fact constellation**. `dim_stations` and `dim_parameters` are shared by both fact tables. Each has its own time dimension: `dim_date` for daily, `dim_month` for monthly.

### `dim_month`
- Columns: `full_month_date` (`DATETIME`, `UNIQUE NOT NULL`), `year`, `month`, `month_name`, `season`, `month_id` (`INT`, primary key, `YYYYMM`).
- `month_id = year*100 + month`. `dim_date`'s formula needed `month*100` because the day had to fit underneath. Here the month sits directly under the year.
- A real date column is kept next to the integer key for the same reasons as `dim_date`: joining against a `DATETIME` fact column and date-aware behaviour in Power BI.
- Generated in Python with `pd.date_range(..., freq='MS')` (month **start**; `'M'` would give month end). 1975-01 through 2026-12, 624 rows, loaded with the same MERGE pattern as the other dimensions.

### `[lf-ogd-smn_m]`, created explicitly
- The daily fact table was auto-generated by Spark, so every constraint had to be added afterwards (NOT NULL first, then primary key, then foreign keys). This table was created with a `CREATE TABLE` that already had everything: composite primary key `(station_id, parameter_id, month_id)`, all three foreign keys inline, and `NOT NULL` on the key columns.
- `month_id` belongs in this primary key. Unlike `date_id` in the daily table, no finer grain is planned, so nothing needs guarding against.
- `value` stays nullable, because real missing measurements exist in the source data.
- `station_abbr` and `parameter` text columns are kept, matching the daily table. They are what the notebook joins on to look up surrogate keys.

### Where the historical comparison is computed
The averages are computed in Power BI (DAX), not precomputed upstream. The fact table keeps raw monthly values, so the comparison can change (which years count as historical) without rebuilding anything.

## Power BI

- Re-selecting tables that were already in the model produced a **cyclic reference** error on `dim_parameters (2)`: duplicate queries for the same table. Only the two new tables should be added.
- Relationships for the new fact table were **not auto-detected** this time. Both were created by hand (`station_id`, `parameter_id`), giving `*:1`, single-direction. A dimension feeding two fact tables did not cause ambiguity in this model.
- `month_name` needed **Sort by column → `month`**, otherwise month names sort alphabetically.
- Measure so far: `Monthly Average = CALCULATE(AVERAGE('lf-ogd-smn_m'[value]), 'dim_month'[year] < YEAR(TODAY()))`.

## Verification Performed

Row counts, no duplicates on the primary key, no NULL foreign keys, and all three foreign keys present on `[lf-ogd-smn_m]`. All passed.
