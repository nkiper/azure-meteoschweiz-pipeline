## Star Schema (Fact Constellation)

Two fact tables at different grains share the station and parameter dimensions. Each has its own time dimension.

```mermaid
erDiagram

    DIM_PARAMETERS ||--o{ LF_OGD_SMN_D : parameter_id
    DIM_DATE ||--o{ LF_OGD_SMN_D : date_id
    DIM_STATIONS ||--o{ LF_OGD_SMN_M : station_id
    DIM_PARAMETERS ||--o{ LF_OGD_SMN_M : parameter_id
    DIM_MONTH ||--o{ LF_OGD_SMN_M : month_id

    LF_OGD_SMN_D {
        int station_id PK "FK -> dim_stations"
        datetime reference_timestamp PK
        int parameter_id PK "FK -> dim_parameters"
        int date_id FK
        float value
    }

    LF_OGD_SMN_M {
        int station_id PK "FK -> dim_stations"
        int parameter_id PK "FK -> dim_parameters"
        int month_id PK "FK -> dim_month"
        datetime full_month_date
        float value
    }

    DIM_STATIONS {

    }

    DIM_DATE {
        int date_id PK
        datetime full_date
        int year
        int month
        string month_name
        string season
    }

    DIM_MONTH {
        int month_id PK
        datetime full_month_date
        int year
        int month
        string month_name
        string season
    }
```

**Daily fact** `[lf-ogd-smn_d]`: composite primary key `(station_id, reference_timestamp, parameter_id)`. `date_id` is a foreign key only, kept out of the PK so finer-than-daily data could be added later without breaking uniqueness.

**Monthly fact** `[lf-ogd-smn_m]`: composite primary key `(station_id, parameter_id, month_id)`. `month_id` belongs in the PK because no finer grain is planned. Created explicitly with all constraints upfront, not auto-generated by Spark, so no constraint backfill was needed.

`value` is nullable on both fact tables because missing measurements exist in the source data.

**Why two fact tables**: mixing daily and monthly rows in one table would make the meaning of a row ambiguous.

**Legacy**: `[legacy_ogd-smn_d_recent]` (wide format, superseded) is retained for reference and is not part of the active pipeline.

## Data Scope Decisions

- **Daily**: current year only (`_d_recent` files), loaded incrementally (max-timestamp filter, then append).
- **Monthly**: 1975 onward (50 years), loaded through the same route (MeteoSchweiz, then local, ADLS `raw/`, Databricks, Azure SQL), with a `dim_month` join in place of `dim_date`.
- **Daily history was not loaded.** A backfill of 2000 onward was started, but the Basic tier's 2 GB limit made it impractical, and daily granularity isn't needed to compare this year against historical averages. The partial load was deleted and monthly data replaced it.

**Open item**: how new months get added to `[lf-ogd-smn_m]` over time (re-run, incremental append, or leave static) is not decided yet.
